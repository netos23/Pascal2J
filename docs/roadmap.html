Part 0

How to use this roadmap

You have four books that disagree with each other in useful ways. Read them as four opinions on the same problem, not as four chapters of one manual.

Every part below has the same shape: goal, deliverable, the decisions that are genuinely yours to make, a reading strip with chapter pointers, traps that cost people weeks, and tasks — small, self-contained pieces of work that teach something you cannot learn by reading. Tasks are marked (1) an evening, (2) a weekend, (3) a week or more.

Nothing here is implemented for you on purpose. A compiler is one of the few programs where the design decisions are the education; if you take a decision from a document instead of making it, you will hit the consequence three months later without the context to understand it.

Part 1

Scope: which Pascal are you writing?

Undecided scope is the most common reason hobby compilers die. Fix the dialect before you write the lexer, and write the exclusions down.

“Pascal” is at least four languages: ISO 7185 (Standard Pascal, 1983), ISO 10206 (Extended Pascal, 1990), UCSD/Turbo Pascal, and Delphi / Object Pascal. They differ in ways that reach all the way into your back end — Turbo strings are length-prefixed and assignable, ISO strings are packed array[1..n] of char with different assignment rules; Turbo has units, ISO has one monolithic program; Turbo short-circuits boolean operators, ISO does not specify the order of evaluation at all.

Recommendation Target ISO 7185 level 0 (no conformant array parameters) as the specification, plus a short, explicit list of Turbo-flavoured conveniences you allow. Reason: 7185 is a real, finite, freely available standard with a conformance test suite in the wild, and “does the standard permit this?” is then always an answerable question. “What would Turbo do?” is not.

Feature triage

Put every language feature into exactly one of three buckets and keep the table in the repository. It is the single most useful artefact of the whole scoping exercise, because it turns “this program does not compile” into either a bug or a documented non-goal.

BucketFeatures
Core

Semantics you cannot reproduce exactly, and must document

Start docs/DEVIATIONS.md at the same time as the lexer. Every entry is a line of the form standard says X; Pascal2J does Y; because Z. Candidates you will hit:

  • Integer overflow. ISO makes it an error; the JVM wraps silently. Decide: wrap (fast, wrong), or check with Math.addExact and friends (correct, and on HotSpot nearly free because it is intrinsified — measure it, this is Task 1.3).
  • Real arithmetic and output format. ISO specifies a default floating output format that is not Java's Double.toString. Matching it exactly is a week of tedium; matching x:w:d field notation is a day and worth it.
  • dispose and dangling pointers. On a garbage-collected host, dispose cannot make a pointer dangle. Either make it a no-op or (better for teaching) poison the cell in debug builds so use-after-dispose is detected rather than silently working.
  • Variant records used for type punning. The standard says reading a field of an inactive variant is an error; real programs do it deliberately. You cannot reinterpret an int as a float through a JVM object field. Decide early whether variants are a tagged union (safe, breaks punning) or you exclude them.
  • Uninitialised variables. ISO leaves them undefined; the JVM zero-initialises everything. Your programs will be more defined than the standard. That is fine, but a program that relies on it is not portable — consider a definite-assignment warning (Part 10).
  • Evaluation order and short-circuiting. See Part 11; the choice changes generated code and program meaning.
From your own repository testSourses/ok/test0.pas is filed under ok/ but is not valid ISO Pascal: var c := 'y' has no type, const 9n : integer = 0 is not an identifier, a typed const with an initialiser is a Turbo extension, const appears after var, and procedure v(); has empty parentheses that ISO does not allow. That single file contains at least five dialect decisions. Splitting your corpus into ok/ and reject/ and justifying each verdict against the standard is genuinely the best first day of work on this project — it forces every question in this part to the surface before any code depends on the answers. (While you are there: rename to testSources/.)
Tasks 1.1 (1) Fill in the triage table for your grammar; any production you cannot place is a production you do not understand yet.
1.2 (2) Classify every file in testSources/ as accept or reject, with a one-line standard citation for each reject. Design the annotation format now — e.g. a comment {! expect error E0102 at 3:8 !} — because Part 4 will consume it.

Questions Does your grammar allow the ISO declaration order (label, const, type, var, procedures, in that order, each at most once) or the Turbo free order? — Which decision makes your parser simpler, and is “simpler parser” a good reason to restrict a language? — If you accept both, where does the diagnostic live: in the parser or in a later check, and which gives the better error message?
Part 2

Architecture and the front/back boundary

You asked for a shared front end and a replaceable back end. That is the right shape, and it is worth being strict about: the boundary is the deliverable of stage 1, not the .class files.

The pipeline

Why two IR levels, and not zero or three

Wirth uses none: his parser calls the code emitter directly. That works because Oberon-0 is designed for it and he does no optimisation. Appel uses one tree IR plus a canonicalised linear form. Dragon describes three-address code. For you:

  • HIR — a typed, desugared tree. Names resolved, every implicit conversion made explicit, for rewritten, with eliminated, constant expressions folded. Still structured: loops are loops. It is the last form in which a source-level debugger or a pretty-printer is easy.
  • MIR — a control-flow graph of basic blocks over three-address instructions, in SSA form, with an explicit check vocabulary (range check, nil check, index check, overflow check) so the optimiser can remove them. This is what both back ends consume.

Resist a third level. The temptation is a “LIR” close to JVM bytecode; you do not need it, because the JVM is a stack machine and post-order traversal of MIR expressions already gives near-optimal stack code.

The one non-obvious recommendation in this document Make MIR printable and re-parseable from day one: pascal2j --emit=mir foo.pas writes foo.mir, and pascal2j --from-mir foo.mir --backend=jasmin reads it back. It costs perhaps two days. In return: your back end gets unit tests that do not involve Pascal at all, your optimiser gets golden-file tests that a human can read in a diff, you can hand-write pathological MIR to test the back end, and in stage 2 you can develop your VM against .mir files without the front end in the loop. Every serious compiler has this (LLVM's .ll, Cranelift's CLIF) and every student compiler that lacks it ends up debugging the front end and back end simultaneously.

Enforcing the boundary

“Separate front end” is a property you have to defend mechanically, because the first deadline will tempt you to sneak a JVM detail into the type checker (a descriptor string, a slot number, a java/lang/String). Make it impossible:

  • Separate Gradle modules, with :frontend having no dependency on :backend-jasmin — the compiler then rejects the shortcut for you.
  • The driver depends on both and wires them via an interface: 
    interface Backend {
    val id: String                       // "jasmin", later "dvm"
    fun emit(program: MirProgram, opts: BackendOptions): List<Artifact>
}
  • A negative test: ./gradlew :frontend:check must pass with :backend-jasmin absent from the build entirely.
Questions What, exactly, belongs to the front end when the back ends differ this much? Integer widths, for instance: is “integer is 32-bit two's complement” a language fact (front end) or a target fact (back end)? — Where does the decision to represent set of char as four 64-bit words live? — If stage 2's VM is register-based and untagged, does MIR need a notion of value size, and if you add one, is MIR still target-independent or have you smuggled a target in?
Tasks 2.1 (2) Write the MIR data types and its printer before writing the code that produces MIR. Hand-write three .mir files by hand (a loop, a call, an array store) and make the printer round-trip them.
2.2 (1) Draw your own version of the diagram above, and for each arrow write down what data crosses it and what invariants hold there. Put it in docs/. When you break an invariant in four months, this drawing is what tells you which side is wrong.

Part 4

Foundations: sources, spans, diagnostics

The quality of a compiler, as experienced by its users, is almost entirely the quality of its error messages. Build the machinery before the phases that need it, or you will retrofit spans through fifty classes.

Goal

A diagnostics engine that every later phase reports through, and a source map that turns byte offsets into human positions.

Design decisions

  • Spans, not line/column. Store (startOffset, endOffset) as two Ints in every AST node; compute line and column lazily from a line-start index built once per file. Line/column in every node is memory you pay for and a conversion you repeat.
  • Stable error codes. E0102, not a message string. Codes let tests assert on meaning rather than wording, let you add --explain E0102 later, and let you change the prose freely.
  • Structure, not strings. A diagnostic is {severity, code, primarySpan, message, notes[], helps[]}. Rendering is a separate concern, so you can add JSON output for an IDE without touching any phase.
  • Fail-soft. Phases return partial results plus diagnostics; only the driver decides whether to continue. An error type and an error symbol that absorb further errors silently are what stop one mistake producing forty messages (Appel ch. 5 makes this point about semantic analysis specifically).
  • Determinism. The compiler must be a pure function from inputs to outputs, including the order of diagnostics. Use LinkedHashMap, never iterate a HashSet into output, sort by span before rendering. Golden tests will punish you otherwise, non-reproducibly, on someone else's machine.
Tasks 4.1 (1) Implement the caret renderer: source line, underline of the primary span, notes beneath. Handle tabs (a tab is not one column) and multi-line spans.
4.2 (1) Build the test harness that reads {! expect E0102 at 3:8 !} annotations out of a reject/ file and asserts the compiler produced exactly that set — no more, no fewer. The “no more” half is what catches cascading-error regressions.
4.3 (2) Add --emit=tokens|ast|hir|mir|jasmin to the driver on day one. Every phase becomes independently inspectable, and every bug report becomes reproducible with one command.
Questions When is it right to stop after a phase and when should you push a partial result forward? (A parse error usually stops semantic analysis; a type error usually should not stop checking the rest of the program.) — What is your policy for the second and subsequent errors caused by the same root mistake, and how will you test that the policy holds?
Reading Appel ch. 4 §“abstract syntax positions” and ch. 5 on error types absorbing cascades. Wirth ch. 7 — his whole error strategy in two pages; note how cheap it is and how much it buys. Dragon §1.3, §4.1.3–4.1.4 on error-recovery strategies and their trade-offs.
Part 5

Lexical analysis

The easiest phase, with three genuine traps in Pascal specifically. Hand-write it; a generator buys you nothing at this size and costs you control of error messages.

Deliverable

A lexer producing a token stream with spans, plus golden token dumps for the corpus.

The three Pascal traps

  • 1..3 versus 1.5. Pure maximal munch lexes 1..3 as the real number 1. followed by .3, and your own test file contains array [1..3]. The fix is one character of extra lookahead: on a digit sequence followed by ., peek the character after the dot; if it is another ., emit the integer and leave both dots. This is the textbook example of why maximal munch needs a backtracking escape hatch, and it is worth understanding as theory, not just as a patch — the same issue is why C needs >> disambiguation in templates and why Pascal's designers regretted nothing.
  • Case insensitivity. Begin, BEGIN and begin are one keyword; Foo and foo are one identifier. Fold for lookup but keep the original spelling for diagnostics, so the error says Foo the way the user wrote it. In Kotlin, fold with lowercase() and be aware that a locale-sensitive fold turns I into a dotless ı in Turkish locales; lowercase() on Kotlin is locale-independent (it is Locale.ROOT semantics) but String.toLowerCase() from Java is not. A compiler whose behaviour depends on the machine's locale is a real bug that has shipped in real products.
  • Comments. { ... } and (* ... *) are both comments, and in ISO Pascal a comment opened with { may be closed with *). They do not nest (Turbo optionally nests them). An unterminated comment at end of file must produce a diagnostic pointing at the opening brace, not at EOF — that single detail is the difference between a five-second fix and a ten-minute hunt for the user.

Minor but real: $FF or 16#FF hex forms depending on dialect; character literals #13; string literals with '' as an embedded apostrophe; the fact that a one-character string literal 'a' is a char in Pascal, which makes literal typing context-dependent — a decision you should take in Part 8, not here.

Tasks 5.1 (1) Write the DFA for numeric literals on paper before coding: integer, real with fraction, real with exponent, and the .. escape. Then implement it and check your implementation against the drawing. Dragon §3.4 is the technique.
5.2 (1) Property test: for a randomly generated token sequence, printing the tokens with a single space between them and re-lexing must yield the same sequence. This catches an entire class of lexer bug in twenty lines.
5.3 (2) Measure: lex a 100k-line synthetic file. If you are slower than about 10 MB/s you are probably allocating a String per token; intern identifiers into a symbol table of Int ids instead and measure again. (Worth doing once, for the lesson in how compilers actually spend time.)
Questions Should the lexer or the parser decide that 'a' is a char rather than a string? — Do you emit comments and whitespace as trivia attached to tokens (needed later for a formatter or an IDE) or discard them (simpler now)? What does that choice cost if you change your mind at M6? — Is the keyword/identifier distinction made in the DFA or by a table lookup after it, and which one does Wirth use, and why?
Reading Dragon ch. 3 entire — §3.3 regular expressions, §3.4 recognition, §3.6–3.7 NFA→DFA and minimisation. Read §3.5 on Lex only to decide not to use it. Wirth ch. 3 (regular languages) and the scanner in ch. 7 — roughly 60 lines of Oberon, for a complete language. Appel ch. 2 — particularly the discussion of why longest-match plus rule priority is the right specification.
Part 6

Parsing and the AST

Pascal was designed to be parsed by recursive descent by a human with a pencil. Take the gift.

Design decisions

  • Recursive descent for declarations and statements, precedence climbing (Pratt) for expressions. Writing factor/term/simpleExpression/expression as four mutually recursive functions, the way the grammar is written, is also fine and is what Wirth does; precedence climbing is the same thing with the level as a parameter. Do the naive version first, then refactor to Pratt and notice they produce identical trees — that refactor is a good half-day of insight.
  • An LL(1) check, mechanically. Do not assume your grammar is LL(1). Compute FIRST and FOLLOW for every production with a small script over your grammar file and print the conflicts. Every conflict is either a bug in your grammar or a place your parser needs extra lookahead — and you want that list explicitly, not discovered one at a time by failing tests.
  • Error recovery: FOLLOW-set panic mode. Wirth's technique (ch. 7) is to pass each parsing procedure the set of tokens that may legally follow it, and to skip input until a token in that set appears. It is about thirty lines and gives good behaviour. Appel §3.4's Burke–Fisher local repair is better and considerably more work; read it, implement it later if at all.
  • AST shape. Sealed interfaces and immutable data classes in Kotlin, one node type per construct, every node carrying a NodeId and a span. Keep the results of later phases in side tables keyed by NodeId (types: Map<NodeId, Type>, symbols: Map<NodeId, Symbol>) instead of mutable fields on nodes. You get immutability, you can run a phase twice, you can throw a phase's results away, and you never wonder whether a field has been filled in yet. The cost is one indirection per lookup, which is free at this scale.
Traps Dangling else — the grammar is ambiguous; the rule is “bind to the nearest unmatched if”, which recursive descent gives you for free simply by consuming else greedily in the inner call. Know that you relied on an implementation accident and write the test.
Error recovery that does not consume input loops forever. Invariant: every iteration of a recovery loop either consumes a token or exits. Assert it.
Semicolons. Pascal's ; is a separator, not a terminator, so begin a; b; end contains an empty statement — legal, and the source of the classic “; before else” error. Decide whether to warn.
Tasks 6.1 (2) Write the FIRST/FOLLOW calculator over your own grammar file and commit the conflict report as a golden test. When you extend the grammar later, a new conflict shows up in a diff.
6.2 (1) Take twenty programs from your corpus, delete one token from each at random, and require exactly one diagnostic and a complete parse tree for the rest of each file. This is the fastest way to find out whether your recovery is real.
6.3 (2) Implement an AST pretty-printer, then a property test: parse(print(parse(src))) == parse(src). Cheap, and it catches precedence and associativity errors that eyeball tests miss.
6.4 (1) Ambiguity hunt: find two different grammars for Pascal expressions, one ambiguous and one not, and explain in a paragraph why precedence climbing resolves the ambiguity without changing the grammar.
Questions Do you want a concrete syntax tree (every token, including punctuation and comments) as well as an abstract one? It is what makes a formatter, an IDE and refactoring possible, and it roughly doubles the size of Part 6. What is it worth to this project? — Where do you put the boundary between “the parser rejects it” and “the parser accepts it and a later check rejects it”? Consider const 9n = 0: is that a lexical error, a syntax error, or a semantic one, and which produces the most helpful message?
Reading Wirth ch. 2, 4, 7 — deterministic parsing conditions and the complete Oberon-0 parser. The clearest exposition of recursive descent in print. Dragon §4.4 (predictive parsing, FIRST/FOLLOW, tables), §4.4.5 (panic-mode recovery). Skim §4.5–4.9 (LR) for literacy; you will not write an LR parser here. Appel ch. 3 (esp. §3.2 predictive parsing and §3.4 error recovery) and ch. 4 (abstract syntax — note his separation of abstract from concrete syntax, and the visitor question). Pierce ch. 3 — not about parsing, but the place to learn the inductive-definition style you will use to specify the AST and prove things about traversals.
Part 7

Scopes, symbols and nesting

Pascal's nested procedures are its defining feature and the place where the JVM will fight you hardest. Decide the strategy here, in the front end, and make the back end's job mechanical.

Deliverable

Every identifier occurrence resolved to a symbol, or diagnosed. A dump format for scopes that you can golden-test. A computed escape flag on every local variable.

The problem

A procedure nested inside another can read and write the outer procedure's locals:

procedure Outer;
var total: integer;          { lives in Outer's frame }
  procedure Add(x: integer);
  begin
    total := total + x       { non-local access, one level up }
  end;
begin total := 0; Add(5); writeln(total) end;

On a conventional machine you solve this with a static link (a pointer in each frame to the frame of the lexically enclosing procedure) or a display (an array indexed by nesting depth). Wirth ch. 12 and Dragon §7.3 both cover this; Appel ch. 6 is the most complete treatment and is where you should start.

The JVM gives you neither: a method has locals, and nothing else can reach them. Your options:

StrategyWhat it meansCost
Heap frame objects Each procedure whose locals are captured gets a generated class Outer$Frame with a field per captured variable; inner procedures become static methods taking the frame as an extra parameter, plus its own parent chain for deeper nesting. One allocation per activation of an enclosing procedure; field access instead of local access. Simple, uniform, obviously correct.
Lambda lifting
(closure conversion)		 Add each captured variable as an extra parameter to the inner procedure, and thread it through all call sites. Classic; see Appel ch. 15. Only works directly for variables that are read, not assigned — an assignment must be visible to the outer frame, so a mutable captured variable still needs a cell. Parameter lists can explode under deep nesting.
Everything on the heap Every local of every procedure becomes a field of a frame object. Trivially correct, uniformly slow, and it defeats HotSpot's register allocation. Do not.
Recommendation Heap frame objects, plus an escape analysis so that only actually-captured variables move. In practice the overwhelming majority of locals in real Pascal are never touched by an inner procedure, so they stay in JVM locals where HotSpot can put them in registers. Escape analysis here is ten lines — walk the body of each nested procedure, mark every non-local symbol it references — and it is the same analysis you need for var parameters (Part 8) and again in stage 2 for scalar replacement. It is the highest value-per-line of code in the whole front end.

Part 8

Types and semantic analysis

The longest milestone, and the one where Pierce earns his place on your shelf. Write the rules down in inference-rule notation first; implement them second; the implementation then has a specification to be wrong against.

Deliverable

A type for every expression, a diagnostic for every ill-typed program in the reject corpus, and a document — half a dozen pages — containing your typing rules.

Write the rules down

Pascal is simply typed, so the whole type system fits in a few pages of judgements in Pierce's notation. Start with the environment and the shape of the judgement:

Γ ⊢ e : τ            "in context Γ, expression e has type τ"
Γ ⊢ s ok            "in context Γ, statement s is well formed"

                Γ ⊢ a : array[ι] of τ      Γ ⊢ i : ι'      ι' ≲ ι
(T-Index)      ----------------------------------------------------
                        Γ ⊢ a[i] : τ

                Γ ⊢ l : τ₁  lvalue(l)     Γ ⊢ e : τ₂     τ₂ ≲ τ₁
(T-Assign)     ----------------------------------------------------
                             Γ ⊢ l := e ok

The interesting content is entirely in the relation written ≲ — Pascal's assignment compatibility, which is not type identity and not subtyping in Pierce's sense. It says roughly: identical types are compatible; integer is compatible with real (with an implicit widening); a subrange is compatible with its host type and vice versa subject to a runtime check; a set type is compatible with another set type whose base types are compatible; strings of equal length are compatible. Writing this relation out precisely, as rules, is the single most valuable half-day in Part 8 — and it will expose at least three cases you had not thought about.

Why this is not subtyping In a subtyping system (Pierce ch. 15) S <: T means every value of S is a value of T, and coercion is free. Pascal's subrange compatibility is different: assigning integer to 0..9 is permitted by the type system but may fail at runtime. It is a checked coercion, closer to a cast with a proof obligation than to subsumption. Notice what this means for you: the type checker's job is not only to accept or reject, but to record where a runtime check is required — and that record is what the optimiser will later try to discharge statically (Part 10). Make the check an explicit node in HIR at the moment the type rule licenses it; do not leave it implicit for the back end to remember.

The checklist

Semantic analysis is a long list of small rules, and the way to not miss any is to keep the list. At minimum: undeclared identifier; duplicate declaration in one scope; type identity for var-parameter arguments (compatibility is not enough — a var parameter requires an identical type and an lvalue argument); assignment to a const; assignment to a for-loop control variable inside its own loop (ISO forbids it; a nice check to implement because it needs a small scope-like stack of “currently controlled” variables); a function that never assigns its result; argument count and kind; case label duplication and type agreement with the selector; set element ordinality and base range; array index type must be ordinal and bounds must be constant; enumeration constant scope leakage; with-statement field injection and its shadowing rules; the required-procedure special cases.

write and writeln are not procedures They are variadic, they accept arguments of several unrelated types, they accept the value : width : digits syntax that appears nowhere else in the grammar, and writeln takes an optional first argument that is a file. No user procedure can be declared like that. Do not try to make them fit your ordinary call-checking path; give them a dedicated checker and a dedicated HIR node. Every Pascal implementation does this, and discovering why is worth an hour of trying not to.
Type identity in Pascal is by name, mostly type A = array[1..10] of integer; B = array[1..10] of integer; — are A and B the same type? In ISO Pascal, no: they are distinct types and not assignment compatible, though they are structurally identical. But an anonymous type written inline in two var declarations is also two distinct types, which is why var x, y: array[1..10] of integer; makes x and y compatible (one declaration, one type) but splitting the line into two makes them incompatible. Implement types as interned objects with identity, created once per syntactic type denoter, and this falls out for free. Get it wrong and you will rediscover it via a very confusing bug.

Part 9

HIR: desugaring and lowering

A short phase that pays for itself by deleting language features. Everything you desugar here is a feature neither back end ever has to know about.

What HIR removes

  • for loops → explicit initialise / test / body / increment (see the trap below — this is not as easy as it looks).
  • with statements → a temporary holding the record reference, and fully qualified field accesses.
  • repeat → a loop with the test at the bottom; case → a multiway-branch node on an ordinal, with the labels normalised to integers.
  • Implicit conversions → explicit Convert nodes; implicit range checks → explicit Check nodes; string literal padding; set construction from element lists.
  • Nested procedures → flat list of procedures with explicit frame parameters (the decision from Part 7 is applied here).
  • var parameters → explicit cell/reference passing.
  • Named constants → literals; constant expressions → values.
The for loop is a trap, and a good exercise Pascal's for i := a to b do S is not C's for. (1) a and b are evaluated once, before the loop. (2) If a > b the body never executes. (3) The control variable is undefined after the loop — you may not read it. (4) The body may not assign to it. And the one that catches everyone: (5) if b is the largest value of the control variable's type, the obvious lowering i := a; while i <= b do begin S; i := i + 1 end overflows or loops forever on the last iteration. The correct shape is a bottom-tested loop guarded by an initial a <= b test, with the increment guarded by i <> b: 
if a <= b then begin
  i := a;
  loop: S; if i = b then goto done; i := succ(i); goto loop;
  done:
end
Write the test with b = maxint before you write the lowering. Then check what your favourite real compiler does with it.
Questions Is HIR a separate data type, or is it “the AST with some node kinds forbidden”? The first costs you a second tree definition and a translation; the second costs you an invariant that is not checked by the type system. Which mistake would you rather debug? — Should HIR be typed (every node carries its Type) or is the type information consumed and discarded by lowering? Consider stage 2, where an adaptive VM might want source types for specialisation. — Does any optimisation belong at HIR level rather than MIR? (Consider: with-common-subexpressions, string-literal interning, and inlining of trivially small procedures — inlining before closure conversion can be much more effective.)
Reading Appel ch. 7 — translation to intermediate representation; the discussion of why an IR tree is simpler than the AST and what “lower” means. Dragon §6.1 (variants of syntax trees), §6.4 (translation of expressions), §6.9 (intermediate code for procedures).
Part 10

MIR: control-flow graph, SSA, and the optimiser

The part of the project where you will learn the most, and the part where it is easiest to waste six months producing no measurable improvement. Both facts are worth taking seriously.

The representation

A program is a list of procedures; a procedure is a set of basic blocks with a single entry; a block is a list of instructions ending in exactly one terminator. Instructions are three-address and define at most one value. In SSA form each value is defined exactly once and blocks begin with φ-nodes.

proc Sum(n: i32) -> i32 {
bb0:
    v0 = const 0
    br bb1
bb1:                                  ; phis first, always
    v1 = phi [v0, bb0], [v4, bb2]     ; total
    v2 = phi [const 1, bb0], [v5, bb2]; i
    v3 = icmp.sle v2, n
    br v3, bb2, bb3
bb2:
    v4 = add.ovf v1, v2               ; checked add: traps on overflow
    v5 = add v2, 1
    br bb1
bb3:
    ret v1
}

Four decisions that will matter later

  • Safety checks are instructions, not implicit behaviour. check.range v, lo, hi, check.index a, i, check.nil p, add.ovf. If a check is implicit in the semantics of store, no pass can ever remove it. If it is an instruction, removing it is just dead-code elimination once an analysis proves the condition.
  • Aggregates stay structured. No address arithmetic, no load [base + 4*i + 8]. Use elem a, i and field r, 3. Appel and Dragon both lower to address arithmetic because they target real machines; the JVM cannot express it, and your stage-2 VM does not have to either. This is the main place where you should deliberately deviate from the books, and knowing why you are deviating is the point.
  • Keep a source position and a live-variable map on every instruction that can trap. You do not need them in stage 1 beyond error messages. In stage 2 they become your deoptimisation metadata, and retrofitting them into an optimiser that has already destroyed the mapping is genuinely painful. This is the cheapest thing you can do now to make stage 2 possible later.
  • SSA construction algorithm. Cytron et al.'s dominance-frontier algorithm is what Appel ch. 19 and Dragon §9.5.1 teach, and you should understand it. But for a hand-written compiler, Braun et al. (2013), “Simple and Efficient Construction of SSA Form”, builds SSA directly during IR construction with no dominance computation at all, in about 150 lines. Recommendation: implement Cytron once as a learning exercise, then use Braun in the real pipeline, and write down which you would choose for a production compiler and why.

The Jasmin back end

A stack machine is the easiest code-generation target in existence, right up until the verifier disagrees with you. Most of this part is about making the verifier your test oracle instead of your enemy.

Deliverable

A back end that turns MIR into .j text, plus the toolchain step that assembles it, plus a runtime library in Kotlin that the generated code calls.

The shape of the output

.bytecode 49.0                     ; see the verifier trap below
.source  hello.pas
.class public Hello
.super   java/lang/Object

.method public static main([Ljava/lang/String;)V
  .limit stack 2
  .limit locals 1
  .line 1
  getstatic    java/lang/System/out Ljava/io/PrintStream;
  bipush       42
  invokevirtual java/io/PrintStream/println(I)V

Program → one public class. Global variables → static fields. Procedures and functions → static methods (they are all statically bound; you have no objects). Nested procedures → static methods taking a frame parameter, per Part 7. The main program body → main([Ljava/lang/String;)V.

The verifier trap, and why .bytecode 49.0 is on the first line Class files of version 50 (Java 6) and above are verified by the type-checking verifier, which requires a StackMapTable attribute on every method with branches: for each jump target, an explicit description of the types on the operand stack and in the locals. Computing those correctly is a data-flow analysis with a type lattice including uninitialized and merge rules over class hierarchies — a real project in itself, and a dreadful thing to debug while also debugging your code generator. Class files of version 49 and below use the older inference verifier, which computes the same information itself and needs no attribute. So: emit 49.0 and the whole problem disappears. Modern JVMs still load version 45–49 class files. Do not plan to use -noverify/-Xverify:none instead: it is obsolete and ignored on current JDKs. If you later want modern class files, switch from Jasmin to ASM with ClassWriter.COMPUTE_FRAMES and let the library do it. (That switch is itself a good week of work and teaches you what the attribute contains.)
Three more things the verifier will catch, painfully .limit stack / .limit locals must be at least the true maxima. Compute the stack limit by abstract interpretation over your CFG: the stack depth at a block's entry must be the same on every incoming edge — assert that, because a mismatch is also a verify error and your own assertion has a much better message than VerifyError: Inconsistent stack height.
Category-2 values. long and double occupy two local slots and two stack words. A slot allocator that assumes one slot per variable produces code that verifies for a while and then does not. Write the test with a real local between two integer locals.
Stack discipline across jumps. Your local goto is only safe between statement boundaries, where the operand stack is empty. Assert “stack is empty at every statement boundary” in the emitter; it makes an entire class of bug impossible.

Boolean expressions: the single most useful idea in Appel

How do you compile if (a < b) and (c < d) then S? Naively: compute a < b as a 0/1 value on the stack, compute c < d, iand, then ifeq past the body. That works and is bad code — the JVM has no comparison instruction that produces a boolean, so each comparison becomes a branch, two loads and a jump. Appel §7.2's answer is to give the translator three kinds of result:

  • Ex — an expression producing a value;
  • Nx — a statement producing nothing;
  • Cx — a conditional: something that, given a true-label and a false-label, jumps to one of them.

with conversions between them. A comparison is naturally a Cx; and of two Cx's is a Cx that threads the labels; and only when a boolean genuinely needs to be a value (stored in a variable, passed as an argument) do you convert Cx → Ex by materialising 0 or 1 around a branch. The generated code for the example above becomes two compare-and-branch instructions and no arithmetic at all. Implement this; it is perhaps 100 lines and it is the difference between a toy code generator and a real one.

A semantic question you must answer first The Cx translation naturally short-circuits. ISO Pascal does not require short-circuit evaluation of and/or, and does not require full evaluation either — it leaves the order unspecified, which means (p <> nil) and (p^.x = 1) is not portable Pascal even though every practical compiler makes it work. Turbo Pascal has a switch ($B). So: which do you implement, do you offer both, and if you offer both, does the choice live in the front end (different HIR) or the back end (different code for the same HIR)? Whichever you pick, note that a program's meaning now depends on it, so it belongs in DEVIATIONS.md and in a test.

Part 12

Testing, conformance and measurement

A compiler is a program whose bugs are silent: it produces output that looks fine and is wrong. The testing strategy is therefore part of the architecture, not an afterthought.

Six kinds of test, in increasing order of value per hour

  1. Unit tests on the lexer and on small utilities. Cheap, necessary, low yield.
  2. Golden files. --emit=tokens|ast|mir output committed next to each source file. A diff shows you exactly what a change did. The single best return on effort in the whole list, which is why Part 2 insists on a printable IR.
  3. Diagnostic fixtures. Every reject program asserts the exact set of error codes and positions. Asserting “no extra diagnostics” is what keeps cascades under control.
  4. Execution tests. Run the compiled program, compare stdout byte for byte with an expected file.
  5. Differential testing. You have three executors (MIR interpreter, JVM back end, later your VM) and the outside world has Free Pascal (fpc) and GNU Pascal. Any disagreement is a bug in exactly one of them, and finding out which is always instructive.
  6. Metamorphic testing. -O0 and -O2 must produce identical output. No expected values needed, so you can point it at any Pascal program, including ones you did not write. This is how you find optimiser bugs at scale.
Tasks 12.1 (2) Fuzz the front end: feed it random bytes, random token sequences, and mutated valid programs. The invariant is not “it compiles” but “it never throws an uncaught exception and never hangs”. Jazzer or a hand-rolled mutator both work.
12.2 (3) Write a random program generator for a subset of Pascal that is guaranteed to terminate and whose expected output you can compute (e.g. arithmetic over bounded integers, loops with fixed trip counts). This is a Csmith-style oracle and it will find optimiser bugs you would never write a test for. Constraining generation so that programs are both interesting and well-defined is the hard, interesting part.
12.3 (1) Set up the benchmark harness before M11: five programs (a sieve, matrix multiply, n-body, a recursive one such as Ackermann or binary trees, and one set-heavy or string-heavy program), each run with proper JVM warm-up, reporting steady-state and first-run times separately. Part 13

Stage 2: your own bytecode and an adaptive VM

This is a second project of comparable size to the first. The point of the architecture in Part 2 is that it starts from a working, tested MIR rather than from nothing.

What “dynamic adaptive” actually buys a statically typed language

Be precise about this early, because it determines your whole design. Adaptive optimisation earns its keep in dynamic languages mostly by discovering types — inline caches, type feedback, speculative monomorphisation. Pascal hands you all the types up front. So what is left?

  • Profile-directed layout and inlining: which call sites are hot, which branches are taken, which loops are worth compiling at all. Available only at runtime.
  • Value and range speculation: this array is always length 100; this divisor is never zero; this subrange variable is always within bounds. These let you delete checks that static range analysis could not prove — with a guard and a deoptimisation path when the speculation fails.
  • Escape analysis and scalar replacement of your frame objects and var-parameter cells, using runtime knowledge of which calls actually happened.
  • Tiering: interpret cold code (fast to start, small memory), compile hot code (slow to produce, fast to run). Almost all of the practical benefit for a compiler like yours.
  • On-stack replacement: entering optimised code in the middle of a long-running loop. Without it, a program with one hot loop in main never benefits at all.

Design decisions, in the order you must take them

DecisionOptions, and the consideration that usually settles it
Stack or register ISA Register. Your MIR is already three-address and in SSA form, so lowering is near-trivial; register machines execute far fewer instructions per program, which matters enormously for an interpreter where dispatch dominates; and every optimisation you already wrote applies directly. A stack ISA is easier to verify and more compact — that is why the JVM chose it — but you already have a stack back end. Read Shi et al., “Virtual Machine Showdown: Stack Versus Registers”, and the Lua 5.0 implementation paper before deciding against this.
Encoding Fixed 32-bit words (simple decoding, wasteful) or variable-length bytes (compact, branchy decoder). Start fixed; you can change it later precisely because the assembler and disassembler are separate programs.
Implementation language A serious fork in the road. Writing the VM in Kotlin keeps one toolchain and lets you reuse the compiler's data structures — but you inherit the JVM's constraints exactly where they hurt an interpreter most: no computed goto, no control over memory layout, no tail calls, and you would be running a JIT on top of a JIT. Writing it in Rust or C gives you threaded dispatch, real memory layout control, and honest measurements. Recommendation: prototype the interpreter in Kotlin to validate the ISA (weeks), then rewrite in Rust/C if you want real performance work (months). Be honest about which project you are doing.
Memory management You now own it. Appel ch. 13 is a complete short course: mark-sweep, reference counting, copying collection, generational. A semispace copying collector is about 300 lines and is the right first one. It requires precise root finding, which requires stack maps at safepoints — which is the same machinery as deoptimisation metadata.
Deoptimisation The hardest single piece. To abandon optimised code mid-execution you must reconstruct the interpreter's state (locals, stack, program counter) from the optimised frame. That means every speculation point carries a map from interpreter state to optimised locations — and that inlining, constant folding and register allocation must all maintain it. This is why Part 10 told you to attach live-variable maps to trapping instructions from day one. Read Hölzle, Chambers and Ungar, “Debugging Optimized Code with Dynamic Deoptimization” (1992), before you design the IR for tier 2.

A staged plan for stage 2

  1. Specify the ISA as a document, with an assembler and disassembler, before writing the VM.
  2. A verifier for your own bytecode. You will be generating it; you will generate it wrongly; a verifier turns undebuggable crashes into error messages. (Now you understand why the JVM has one.)
  3. A plain interpreter that runs the whole corpus, checked against the MIR interpreter and the JVM back end. Measure it. It will be perhaps 30–100× slower than the JVM. That is the baseline the rest of the work is measured against.
  4. Profiling counters on back-edges and call sites; a tiering threshold; a report of what got hot.
  5. A baseline compiler for hot methods — template-per-instruction, no optimisation, just removing dispatch overhead. Expect a large win for little cleverness. This is where most of your speed comes from.
  6. OSR, so loops benefit.
  7. An optimising tier reusing your MIR passes, plus speculation and deoptimisation.
  8. GC, once allocation matters.
Questions worth answering in writing before you start What measurable goal makes stage 2 a success? (“Faster than the interpreter” is trivially achievable; “faster than the JVM back end” is very hard, because you are competing with two decades of HotSpot. “I understand how HotSpot works because I built a small one” is a perfectly good goal — but say so, or you will judge yourself by the wrong metric.) — Method-based JIT (HotSpot, V8) or tracing JIT (PyPy, LuaJIT)? Tracing is dramatically simpler to get working for loop-heavy code and is a much more unusual thing to have built. — What in your MIR would you change today, knowing stage 2 is coming? Change it now, while there is only one back end to update.

# ADR-007: var parameters are passed as reference cells

## Status
Accepted, 2026-04-11

## Context
The JVM has no way to pass a reference to a local variable. Pascal's var
parameters require call-by-reference semantics that are observable when
the same variable is passed twice, or when the callee also reads a global
that the caller passed.

## Options considered
1. Copy-in/copy-out          - fastest; wrong under aliasing
2. One-element Java array    - one allocation per call; simple
3. Generated Ref classes     - one allocation; typed; more generated code
4. (array, index) pair       - no allocation for array elements; two params

## Decision
(3), with escape analysis so a var parameter that the callee only reads is
passed by value. Task 11.3's program is the regression test.

## Consequences
- MIR needs an explicit Cell type; the DVM back end must implement it too.
- Scalar replacement in the optimiser can undo the boxing; see Part 10.
- DEVIATIONS.md: none - this is conforming behaviour.

Decisions worth an entry, at minimum: dialect and feature triage; short-circuit or not; overflow policy; string representation; array lower-bound handling; var-parameter representation; nested-procedure strategy; class-file version; SSA construction algorithm; pass order; stage-2 ISA shape.

A closing thought on what you are actually building

You have chosen an unusually good project. A Pascal front end is small enough to finish, and Pascal's type system is rich enough (subranges, sets, name equivalence, nested procedures, var parameters) that nothing about it is trivial. The JVM back end forces you to confront a target that is almost but not quite a good fit — non-zero array bases, no static links, no references to locals, a verifier with opinions — and every one of those mismatches is a lesson about what an IR is for. And the second stage, where you write the machine as well as the compiler, closes the loop: you will have built both sides of an interface that your four books mostly present as given.

The thing that will determine whether you finish is not any of the technical decisions in this document. It is whether you always have a compiler that works on some language, and whether you can see it working. Ship the vertical slice in week two, keep the corpus green, measure before you optimise, and write down every decision as you make it. The rest is chapters.
